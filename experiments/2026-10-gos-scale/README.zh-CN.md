# 500 个 skill 的树与依赖边（2026-10-17）

[English](README.md)

## 问题

[Graph of Skills](https://github.com/davidliuk/graph-of-skills)（GoS）报告了两点：一是 skill 超过约 500 个以后，把所有 description 平铺列出来代价太高，不如结构化检索；二是把一个 skill 的前置一起带上（沿依赖边反向遍历）比图本身更重要。holon 以前从没在超过 24 个 skill 的库上试过。这次问两个问题：

1. 在 500 个 skill 的规模下，模型读 holon 式的树，能不能和读平铺列表一样找到任务需要的 skill？少读了多少？
2. 一跳的 `needs` 边（「加载我时，把这些也加载上」）离线写好，写的时候不看任何任务，能不能补上差距？

跑实验之前，先让三个模型代理辩论了一轮：从 GoS 借什么（支持者、怀疑者、维护者，记录在 `debate/`）。三方都否决了向量检索、PageRank 和 MCP 服务器，理由是违背 holon 离线、文件化的设计。三方一致同意的方案是：一跳、有上限的 `needs` 边，横切的 skill 作为根节点的 `needs`，是否采纳由这个实验决定。维护者定的采纳门槛是：召回率比不加边的树高 5 个百分点。

## 设置

- **库**：GoS `skills_500`。
- **任务**：87 个 SkillsBench 任务，每个都标了标准答案 skill，平均 2.63 个，其中 61 个任务需要两个以上。229 个标准答案引用全部在库里。
- **树**（`build_tree.py`）：由模型把 500 个 skill 分组成一棵路由树。每张路由表最多 12 行，分组行用 holon 的 `Use when ...: covers ...; excludes ...` 格式，叶子保留原 description。一共 104 张表，最深 4 层。这只是模型一次性建出来的树，没有按 holon 规则用 `replay` 和反馈调优过。
- **needs**（`needs.py`）：对每个 skill，把它的正文和词面最相近的 25 个 skill 给模型看，让模型挑出 0 到 3 个必须一起加载的（比如它调用的工具、它读写的格式）。这一步没用任何任务文本。结果 40 个 skill 共得到 61 条边。如果只看正文里点名的其他 skill，这类边只覆盖 574 个有序标准答案对中的 15 个，所以单靠名字匹配不够。
- **路由**（`evalscale.py`）：
  - `flat`：把任务和 500 条 description 一起给模型，让它选 skill。
  - `tree`：从根节点的路由表开始，选择往下走哪些行（可以选多行），逐层重复，收集最终到达的叶子。
  - `+needs`：在选中的 skill 之外，再补上它们的 needs，只走一跳。

  全程用同一个模型（`deepseek-v4.1-flash`），只跑了一轮。只测检索，没有真正执行任务。

## 结果

| | 召回率 | 标准 skill 全部找到 | 精确率 | 加载 skill 数 | 读取字符 |
|---|---:|---:|---:|---:|---:|
| 平铺 | 0.900 | 67/87 | 0.842 | 3.02 | 95,188 |
| 平铺 + needs | 0.913 | 69/87 | 0.837 | 3.11 | 95,188 |
| 树 | 0.700 | 45/87 | 0.752 | 2.44 | 8,228 |
| 树 + needs | 0.719 | 46/87 | 0.752 | 2.55 | 8,228 |

按任务需要的 skill 个数，统计标准 skill 全部找到的任务数：需要 1 个的，平铺 26/26、树 21/26；需要 2 个的，平铺 15/20、树 7/20；需要 3 个及以上的，平铺 26/41、树 17/41。

## 说明了什么

- **树只读了约十二分之一，但找到的明显更少。** 召回率比平铺低 20 个百分点。树漏掉的 73 个标准 skill 里，平铺找到了 43 个，所以大部分是路由走错了，不是 skill 本身难找。
- **漏掉的分散在各个领域分支，不是某一组建坏了。** 按顶层分支统计漏掉的数量：文档 15、媒体 14、数据科学 13、软件 13、科学 10，其余合计 8。模型在根节点要从 9 行里选，下一层还要再选一次，哪一步都可能漏掉需要的 skill；任务需要的 skill 越多，越容易漏。
- **9.5 万字符（约 2.4 万 token）对这个模型并不算多。** GoS 的平铺基线会随规模变大而变差，但这次只测检索，在 500 个 skill 时平铺并没有变差。只要整张列表能宽裕地放进模型的上下文，平铺仍是更好的选择。会改变这个结论的是上下文更小的模型，或者大好几倍的库，这两种情况都没测。
- **`needs` 有一点帮助，代价也低。** 平铺的召回率提高 1.3 个百分点，树提高 1.9 个百分点；在树上多找到 7 个标准 skill，另外多加载了 3 个无关的。但这没达到 5 个百分点的门槛，不值得为它新增文件头字段、规则和工具支持。所以 holon 目前**不加** `needs`。边和脚本都留在这里，下次再试。

## 局限

- 只有一个库，树由模型一次性建成，只用了一个模型，只跑了一轮。如果像 `../2026-10-anthropic-skills/` 那样，用树自己漏掉的样本来调优（那次调优让树路由提高了 9 个百分点），或许能补上一部分差距。
- 这里测的是标准 skill 集合的召回率，不是任务成功率；GoS 报的是任务成功率。
- `needs` 是模型一次性挑出来的，人手写的边可能更好，也可能更差。

## 复现

```bash
export LLM_BASE_URL=https://your-endpoint/v1 LLM_API_KEY=... LLM_MODEL=deepseek-v4.1-flash
cd experiments/2026-10-gos-scale/scripts
./fetch.sh                 # 把 skills_500 下载到 ../data/；SkillsBench 任务放到 ../data/tasks/
python3 build_tree.py 500  # 生成 ../results/tree_500.json
python3 needs.py 500       # 生成 ../results/needs_500.json
python3 evalscale.py 500 run1
```
